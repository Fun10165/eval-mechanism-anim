## 一、DoG：把"好"拆分清楚的检验工具

### motivation

开场问题：你和大模型聊天时，问的都是定义清楚的问题吗？

大多数人都提过定义不清的要求，例如"帮我写一篇好论文""做一份好 PPT"。这类要求给模型的信息很少，因为模型在训练时已经学会往"人类觉得好"的方向写。模型缺少的是你说的"好"具体指什么：可能是 AI 味轻，可能是不过度防御，而这些说法本身也不清楚。

更麻烦的是，你自己一开始也说不清。你需要亲自参与拆分这个目标；拆分的过程中，你也会越来越清楚自己要什么。

请人逐份评审可以解决一部分问题，可是速度慢、费用高，每次的标准还可能不一样。所以需要一个工具：把人的判断标准记录下来，可以反复运行，每次运行都留下证据。

### design

一句话：DoG（DAG of Goals）是一个由 omp 驱动的检验工具。它把无法形式化的价值判断拆分成一张有向无环图，由 agent 逐项检验产物；人在固定的确认点参与，和 agent 一起反复迭代，把判断标准逐步明确。

五个要点：

1. **只检验产物。** DoG 是 Agentic CI：产物由调用方生成，DoG 只负责检验。产物可以是人写的，也可以是 AI 生成的，只要能保存在硬盘上。检验之前先冻结产物，保证检验对象固定不变。
2. **人在固定的确认点参与。** 用户没有确认的拆分只是草稿，不能代表用户的真实判断。
3. **根节点保留用户原意。** 根节点允许模糊；越往下拆分，判断越精确。
4. **结果如实分级。** 无法判定就报告无法判定，交给人处理。复用的旧结果和被取消的运行，都不能报告成"通过"。
5. **本体极简，容易组合，节省费用。** DoG 只负责三件事：agent 的执行顺序、错误怎样向上传播、图结构是否合法。目标是运行快、费用低。

适用范围：

- **适合**：论文质量、PPT 质量、项目质量、技能文档的指令遵循度，也可以是"今天过得怎么样"。
- **不适合**：能机械判定的目标（例如性能跑分排名），以及非常个人化的偏好。两个产物互相比较的判定方式，需要稍微修改逻辑才能支持。
- **允许混合**：部分叶子可以用程序检查。一个分支如果全部都能用程序检查，这个分支就不归 DoG 处理。

### spec

**1. 和用户一起编写图：三个确认点**

1. 编写之前：复述用户原话和目标，问"我这样理解对吗？"
2. 拆分完第一层之后：把根节点和第一层子节点给用户看，说明每个子节点针对哪种失败方式。然后问：为什么是这些？只有这些吗？其他的为什么排除？能不能更少？
3. 运行之前：把每个叶子的判据和证据要求给用户看，确认这就是用户想要的标准。

**2. 根节点的写法**

- 反面例子："文章必须有 5 个 section、2000 字、3 个实验，每个 section 至少 3 个引用。"这样写，起点就变成了检查清单，DoG 要解决的问题在开头就被跳过了。
- 正面例子："读者只读这份材料，就能相信并使用作者给出的判断。"
- 具体检查交给下层子节点。完整拆分见第二节的论文例子。

**3. 两种判据**

- 程序判据：一个脚本，读取冻结的副本，输出通过、失败或无法判定。
- agent 判据：一句自然语言写的目标，交给一个独立的 agent 会话判定；会话必须提交一次判决。
- 脚本出错、会话超时或者没有提交判决，都记为"无法判定"，交给人处理。
- 每棵组合子树至少要有一个 agent 判据。

**4. 汇总结果**

- 每个叶子单独判定。组合节点用表达式汇总子节点的结果，有四种：全部通过、任意一个通过、至少 n 个通过、结果取反。
- 子节点失败对父节点有三种影响：致命（失败继续向上传播）、可容忍（只算部分问题）、降级（改用一个替代子节点的结果）。
- 组合节点可以再加一个整体判断。整体判断只能把结果往低调整，不能把失败改成通过。
- 根节点的终态有五种：success（必过项全部通过）、partial_success（只有可容忍项失败，且配置允许）、failure（有致命项失败）、needs_replan（有节点无法判定）、cancelled（运行被取消）。

**5. 图里的其他约定**

- 依赖边只决定执行顺序。依赖项到达任意终态就释放，不要求依赖项通过。
- 约束分 hard 和 soft。根节点必须是 hard；soft 节点照常判定，失败时只产生告警。
- 背景材料分两层：general 写 DoG 是什么、判定纪律、证据要求；specific 写这次判什么、用户原话、外部标准清单。两层在创建图时冻结。

**6. 冻结与继承：修改了什么，就只重新判定什么**

- 冻结对象有三种：文件、目录、git 提交。判定会话拿到的是冻结副本。
- 继承标识由两部分计算：对象摘要和判据身份。判据身份是脚本内容，或者目标文本加图的背景摘要。
- 对象、目标文本、背景任一项变化，就重新判定；都没有变化，就复用上次的判决，标为 inherited。复用的结果不能说成"刚刚验证通过"。
- 汇报时，通过要给出关键证据摘要；失败要说明节点、原因、证据；无法判定要说明原因。

**7. 为什么用 omp 驱动**

- DoG 需要用程序大量调用 agent，还要处理超时、没有提交判决这类异常情况。omp 的 RPC 模式方便程序控制这些情况。
- DoG 最早在 dsh（DeepSeek Harness）上开发。dsh 的不兼容改动很多，维护费力，模型在 dsh 里的输出也容易带上 GPT 的写作风格，所以后来换到了 omp。
- 选择 harness 的标准是方便程序调用，以后可以更换。

**8. 目前的局限**

- 判定有随机性：同一份产物多次判定，结果可能不一样。每个判决只来自一个会话，没有投票，也没有自动复检。
- 继承直接复用旧判决：模型行为发生变化时，继承下来的结果察觉不到。
- 图会越写越大：很多节点几乎从来不会失败，却每次都要判定，费用一直上升。第五节的 DDoG 从这个问题出发。

**这一节请听众记住三句话**

1. 只说"好"，模型得不到多少信息；"好"具体指什么，要和用户一起拆分清楚。
2. DoG 把拆分结果写成一张图，由 agent 逐项检验产物，每个结论都附带证据。
3. 无法判定，就如实报告无法判定，交给人处理。

## 二、DoG 的写作方法：判定质量从哪里来

### motivation

技能自迭代已经有很多人在做。我们查找了 2026 年 3 月到 10 月发表的 18 项相关工作，其中 17 项能读到正文（第六节第 8 小节列出）。它们的循环大体相同：运行、判定、修改技能、再运行。决定上限的是判定器：判定器看错了，修改方向就错了；判定器只给一个总分，失败就无法定位到具体原因。

超长程任务的目标大多无法形式化。对这类目标，判定器需要接近一位认真的人类评审：知道"好"指什么，逐条检查，给出证据，看不清时承认看不清。DoG 能不能做到这个水平，取决于图怎样写。所以写作方法单独成一节。

### design

作者给出的三个前提（原话整理）：

1. **每个人都有自己的偏好。** 这是长期存在的价值。模型再怎样迭代，也不能替人决定"你想把什么风格固定下来"。
2. **大模型在定义清楚的小问题上表现好。** 原因有三：一次只做一件事，内在复杂度小；模型拆解任务的能力还没有训练好；人不把问题定义清楚，模型很难按人的预期解决。
3. **所以由人决定怎样拆分，由模型逐个回答拆分后的小问题。** DoG 把一个大的、定义不清的价值判断，换成许多定义清楚的小判断。

在这三个前提下，判定质量来自七个机制：

1. **标准来自人。** 根节点保留用户原意，三个确认点由用户确认。判定器的上限是标准的清晰程度。
2. **抽象层。** 每一层只回答一个问题；父节点是子节点的抽象；同一层使用同一个划分依据。
3. **先写公理，再按失败方式递归拆分。** 拆分结果用三条检验和四个问题检查覆盖与互斥。
4. **叶子足够单一。** 一个叶子只放一个判断，证据能指向具体的句子、页面或数字。
5. **领域知识用来检查，不直接当节点。** 领域条目是反例库和穷尽性检查清单。
6. **判定会话独立、只看冻结证据、允许无法判定。**
7. **写完以后自检，并用版本管理迭代。**

### spec

**1. 一个完整例子：优秀论文的标准**

- 根（公理）："读者只读这份材料，就能相信并使用作者给出的判断。"
- 公理里的每个词都是约束，每个约束得到一条一级性质：
  - "那个判断" → **主张**：被传出去的判断本身。
  - "相信" → **依据**：为什么它可以被相信；以及 **不失真**：材料与真相之间没有系统性偏移。
  - "只读这份材料" → **记录**：别人能不能自己重做。
  - "读者" → **接收**：读者能不能取走这个判断。
- 往下一层，例如"依据"拆成推理和观测：
  - 推理：前提写明；推理链不中断。
  - 观测：观测与主张对应；其他解释被排除；覆盖主张的范围；报告方差；给出人类参照。
- 规模：41 个节点，其中 28 个叶子。
- 严格程度：主张、依据、不失真、记录四组，任一叶子失败即致命；接收组标为可容忍，失败时根节点降为 partial_success，如实记录。
- 判据来源：Nature 编辑标准与报告标准；NeurIPS 检查清单、ICLR 与 ICML 审稿指引（会议口径，这张图没有采用）；三篇代表作用于分离案例（DeepSeek-R1 的 Nature 正式版、GPT-3、Attention Is All You Need）。

**2. 抽象和总结、归纳、分类的区别**

| 做法 | 得到什么 | 问题 |
|---|---|---|
| 总结 | 把已有内容压缩成几句 | 丢掉失败方式，无法判定 |
| 归纳 | 从几个例子里提取共同点 | 覆盖不了没见过的边界 |
| 分类 | 按相似性把条目分组 | 组内没有共同性质，组间会重叠 |
| 抽象 | 找到父性质在下一层的失败方式 | 能继续递归，能检查是否穷尽 |

**3. 递归拆分：三条检验和四个问题**

- 拆分方法：把父节点固定为"成立"，问"它可以怎样失败"。每种失败方式是一个子节点；子节点还能失败，就继续向下拆分，直到判断足够单一，成为叶子。
- 三条检验：
  1. 子节点失败，必然破坏父节点。
  2. 子节点之间互不蕴含。
  3. 拿掉任一子节点，父节点就无法被完整刻画。
- 四个问题（对每个父节点都要回答）：
  1. 为什么是这些子项？
  2. 为什么只有这些？覆盖全了吗？
  3. 其他的为什么不是？它们归属哪里？
  4. 能不能更少？删掉一个子项，父节点还成立吗？
- 回答不出来，说明抽象层还没有写好。

**4. 划分规则与放错分支的检查**

| 划分规则 | 对应的判据 |
|---|---|
| 同一划分依据，每次只用一个差异划分 | 同一层使用同一个抽象面 |
| 穷尽，覆盖被划分的对象 | 覆盖面完整 |
| 互斥，各支互不包含 | 叶子不可再拆，没有重复 |
| 不越级，每级只降一层 | 父节点是子节点的抽象 |

防止子项放错分支，用四个检查：

1. 主语检查：子项失败时的主语，与父项是否为同一个对象。
2. 蕴涵检查：子项失败是否必然破坏父项；毫无影响，说明它属于别处。
3. 修复检查：修复这条失败要修改的是论证、观测、材料还是文本；与父项所在的层级对照。
4. 反向检查：把它拿掉，父项是否残缺；移到别的父项下，是否和别的子项重叠。

判断时看它失败时的对象与动作，不看它用了什么工具。

**5. 叶子与判据的写法**

- 一个叶子只放一个判断。出现以下情况就继续拆分：一个目标里有两个"并且"；判据要同时检查两个互不相关的方面；证据无法指向具体的句子、段落、页面或数字。
- 判据一句话，写清标准和不可接受的形态。
- 判据要求证据：具体的句子、段落、页码、行号、数字或截图路径。
- 判据写"判定什么、什么算不合格"，不写"怎么做"。
- "好""高质量""合理""自然""有深度"这类词，都要换成可以观察的形态。
- 无法判定就让它判定为无法判定，不为了让根节点通过而放宽判据。

**6. 领域知识的三种用法**

- 反例库：每条性质需要真实的失败方式。例如数据污染，是"其他解释没有被排除"的一个实例。
- 穷尽性检查：拿官方清单逐条问"它破坏哪一条性质"。回答不出来的条目，说明结构少了一条性质。
- 分离案例：用代表作品之间的差异检查结构。例如 GPT-3 没有发布代码与权重：记录失败，依据仍然成立；Transformer 论文没有量化不确定性：观测的强度不确定，推理仍然成立。

**7. 判定会话的纪律**

- 一个会话只判定一份冻结对象和一条目标。目标是唯一的标准：不放宽、不扩大、不换成会话自己的口味，不判定目标没有问的内容。
- 会话只读，只读冻结对象，不去找更新的版本。工具只开放 read、grep、glob；不加载扩展、技能和规则。
- 证据要让别人不重复工作也能复核：原文引用、计数、路径、测量值。
- 无法判定是诚实且预期内的结果。猜一个"通过"，是唯一无法挽回的错误。
- 会话退出、超时、崩溃而没有提交判决，一律记为无法判定，不记为通过。

**8. 写完以后：元图自检与版本管理**

- 元图自检：用一张检查"DoG 图写得好不好"的图（do-dog-genesis，19 个节点）判定刚写好的图，重点检查根节点是否忠实于用户原意、抽象层是否清楚、叶子能否再拆分、覆盖是否完整、每个叶子能否只凭冻结对象取得证据。元图判定不了"相对一份没写下来的标准还缺什么"，那份标准要先写进 specific，并由用户确认。
- 版本管理：每张图放进 git；一次迭代只回答一个缺口；提交信息写成"vN：动机 → 机制"；缺口清单分内在矛盾、没有写清楚、扩展需求三类，内在矛盾优先处理。

**9. 术语纪律**

- 抽象和比喻是两回事。比喻借用另一个领域的词，读者无法从字面知道判定条件。
- 不使用比喻词，不使用词典查不到的含义。检查方法：把词换成词典里的定义，句子还能不能判定。
- 一个概念只用一个词，不为同一个意思造同义词。

**10. 证据边界**

- 上面的机制说明 DoG 为什么有可能接近人类评审的水平。要证明"接近人类水平"，需要一组人工判定与 DoG 判定的对照数据；这组数据目前还没有。
- 已经观察到的判定差异：同一份候选，五条规则在一个会话里一起判定时是 5/5 通过；每条规则单独一个会话判定时，S1 判定为失败。此后实验一律采用逐条单独判定。

**这一节请听众记住三句话**

1. 判定质量的上限，是标准的清晰程度；标准由人确认。
2. 拆分按失败方式递归，用三条检验和四个问题检查覆盖与互斥。
3. 判定会话只看冻结证据，必须引用原文，允许无法判定。

## 三、超长程任务：整个应用从 Android 迁移到 HarmonyOS

### motivation

DoG 要检验的产物里，最难的一类来自超长程任务。hmigbot 是一套代理流程，把整个 Android 应用迁移成可以编译运行的 HarmonyOS 应用。

主流 agent 基准不覆盖这类任务。2026 年 8 月，华为的论文发布了 A2H-RepoBench，任务和 hmigbot 相同：把真实的 Android 仓库整体迁移成 HarmonyOS 仓库。论文数据显示，在 5 万到 30 万行的真实应用上，单次迁移要 12 到 44 小时、6,500 万到 2.3 亿 tokens（不含缓存命中）。单次时间是主流长程基准的数倍到数十倍。

再加上评判困难、耦合多、方差大，拿整条流程的最终结果迭代技能，一次比较就要一到两天，失败也无法定位到具体技能。下面先给数据，最后引出贪心链。

### design

1. **任务相同，规模更大。** hmigbot 和 A2H-RepoBench 做的是同一种任务；A2H-RepoBench 的应用有 5 万到 30 万行代码。
2. **时间高出数倍到数十倍。** A2H-RepoBench 单次 12 到 44 小时；主流长程基准单次在几分钟到两小时之间，最长的 SWE-Marathon 单任务上限 10 小时。
3. **tokens 更多。** 按不含缓存命中的保守口径，A2H-RepoBench 单次用量仍然高于多数基准含缓存的平均值。
4. **评判困难。** 代码能编译，说明不了功能完整，也说明不了代理按技能执行；规格、计划这类中间文档没有单元测试可以运行。
5. **耦合多。** 前面阶段的一个小改动，会让后面大量产物失效。
6. **方差大。** 同一个起点、同一个模型、同一段提示，两次运行的时长、阶段分布、检查结论都可能不同。
7. **Jetsnack 只是冒烟测试。** 本机用的 Jetsnack 约 7,500 行，用来验证流程能否完整运行；即便这样小的应用，单次也要 3 到 7.6 小时。

### spec

#### 1. hmigbot 做什么

- 输入：Android 源工程，加一个空的 HarmonyOS 工程骨架。两个路径写在 `.migbot/config.json` 的 `android` 和 `harmonyos` 字段。
- 流程：`/a2h-run` 按固定顺序调用五个技能：`a2h-spec`（规格）→ `a2h-plan`（计划）→ `a2h-execute`（执行）→ `a2h-verify`（验证）→ `a2h-retrospect`（复盘）。中断后按完成标记继续。
- 输出：UI 清单、功能索引、分页规格、迁移计划、ArkTS 代码、HAP 安装包、验证报告、复盘报告。
- 规模：74 个技能、11 种子代理。
- 平台：hmigbot 原本运行在华为的 DevEco Code 上（产品名 hmigbot-deveco）；本实验使用移植到 omp 上的版本（hmigbot-omp 1.6.6）。

#### 2. 同一任务的公开基准：A2H-RepoBench

论文报告的单次迁移开销（ECAT 方法，DeepSeek-V4-Pro，3 次独立运行的平均）：

| 仓库 | 代码行数（千行） | 迭代次数 | 墙钟（小时，约） | tokens，不含缓存命中（百万，约） |
|---|---|---|---|---|
| Gallery | 50 | 38 | 12 | 65 |
| AntennaPod | 120 | 95 | 29 | 180 |
| Meshtastic | 300 | 126 | 44 | 230 |

- 同一篇论文里，Gallery 换成 DeepSeek-V4-Flash：89 次迭代，约 24 小时，约 1.46 亿 tokens。
- 论文对开销的解释："Iterations, wall-clock time, and token consumption all grow with repository scale, roughly tripling from Gallery (50K LOC) to Meshtastic (300K LOC), which reflects the long-horizon nature of the task rather than a limitation specific to ECAT."
- 论文的评判方式：节点匹配（Node Alignment，比较两端代码的语义节点），加上按功能清单逐条判定的 agent 评审（三个仓库分别 323、184、129 条功能）。

#### 3. 和主流基准比较（单个任务、单次尝试）

| 基准 | 单次墙钟 | 单次 tokens（百万） | tokens 口径 |
|---|---|---|---|
| SWE-bench Verified | 未报告（人类时间分档：15 分钟以内到 4 小时以上，4 小时以上只有 3 题） | 4.17（8 个模型平均） | 输入 + 输出，未单列缓存 |
| OpenHarmony Bench（鸿蒙应用开发） | 6.6–32 分钟 | 0.98–3.69 | 服务商报告的 total_tokens，报告时含缓存 |
| Long-Horizon-Terminal-Bench | 平均 88.9 分钟（上限 90 分钟） | 9.79 | 全部提示 tokens 计入 |
| Terminal-Bench 4.0 | 53–124 分钟 | 4.42–58.8 | 排行榜 total_tokens；按字段推算含缓存命中 |
| SWE-Marathon | 上限 2–10 小时 | 中位 7.6，均值 27.2，最大 877.4 | 含缓存 |
| **A2H-RepoBench（同一任务）** | **12–44 小时** | **65–230** | **不含缓存命中** |

怎样读这张表：

- **时间**：A2H-RepoBench 单次 12 到 44 小时，是 Long-Horizon-Terminal-Bench 平均值的 8 到 30 倍，是 Terminal-Bench 4.0 的 6 到 50 倍，是 OpenHarmony Bench 的 20 到 400 倍，也超过了 SWE-Marathon 的单任务时间上限。
- **tokens**：A2H-RepoBench 用的是不含缓存命中的口径，这是最保守的比较方式。即便如此，单次 6,500 万到 2.3 亿 tokens，是 SWE-bench Verified 平均值的 16 到 55 倍，是 SWE-Marathon 含缓存均值的 2.4 到 8.5 倍。
- **同一平台**：OpenHarmony Bench 同样在鸿蒙平台上测 agent，任务是单个功能或单个缺陷，单次只要几分钟到半小时。量级差距来自任务规模，和平台关系不大。
- **同一档的少数例子**：MirrorCode 给每次尝试 10 亿 tokens、7 天的预算；Terminal-Bench Challenges 的初始实验让 agent 运行 12 小时，每个任务费用约 1,000 美元以上。它们和 A2H-RepoBench 一起，属于目前公开数据里最长的一档。
- **Terminal-Bench 4.0 的口径**：排行榜没有说明 total_tokens 是否含缓存。缓存命中字段约占输入字段的 95% 到 97%，按这个比例推算 total_tokens 已经包含缓存命中。这一条是推算，原文没有写明。

#### 4. Jetsnack：冒烟测试用的小应用

- 应用：Jetsnack，Google 官方的 Compose 示例应用，52 个 Kotlin 文件，约 7,500 行。Gallery 的代码量约是它的 6.7 倍。
- 模型：`deepseek/deepseek-flash`（运行时实际路由到 DeepSeek V4.1 Flash），思考强度 max，用 omp 的 RPC 模式驱动。
- 记账：扫描主会话和全部子代理的会话记录，累加每次模型调用的用量。只看主会话会严重少算：同一份候选，主会话费用 0.087 美元，全部会话 6.61 美元。

本机两次完整运行（2026-10，同一起点）：

| 指标 | 第 1 次 | 第 2 次 |
|---|---|---|
| 墙钟时间（小时） | 3.05 | 7.58 |
| 模型调用次数 | 4,102 | 3,750 |
| 工具调用次数 | 5,942 | 5,306 |
| tokens，含缓存（百万） | 782.6 | 835.8 |
| tokens，不含缓存（百万） | 13.1 | 12.3 |
| 模型费用（美元） | 6.69 | 6.61 |

- 7,500 行的小应用，单次也要 3 到 7.6 小时、约 8 亿 tokens（含缓存）。
- 98% 以上的 tokens 是缓存命中的输入：每次模型调用都要重新发送已有的上下文。费用低，是因为 Flash 的缓存命中价格低；模型需要读取的上下文总量仍然很大。SWE-Marathon 的作者在他们的数据里观察到同样的现象：输出只占全部 tokens 的约 0.5%。
- 两次都走完了五个阶段，最后一行都写着 `A2H_PIPELINE=PASS`。同一次运行的验证报告里，CHECK-2（应用身份）有 2 条失败；CHECK-3 视觉检查、CHECK-4 单元测试、CHECK-5 行为验证按运行指令记为跳过。
- 和 A2H-RepoBench 的粗略对照（推算）：Gallery 代码量约是 Jetsnack 的 6.7 倍；不含缓存的 tokens，ECAT 在 Gallery 上用 Flash 约 1.46 亿，hmigbot 在 Jetsnack 上约 1,200 万到 1,300 万。两边的方法不同，这个比例只能作参考。

#### 5. 方差的证据

- 本机两次运行：同一起点、同一模型、同一段提示，墙钟 3.05 小时对 7.58 小时，相差约 2.5 倍。
- 更早两次在 DevEco Code 上的完整迁移（2026-09-18，同一起点、同一模型）：总时长几乎相同（296.2 分钟对 296.0 分钟），阶段分布却相反。执行阶段 99.9 分钟对 248.8 分钟，验证阶段 160.0 分钟对 1.6 分钟。同一条检查 CHECK-2，一次判定通过，一次判定失败。
- 公开数据：在 SWE-bench Verified 上，同一个任务多次运行，token 用量最多相差 30 倍（Bai et al.）。超长程任务里，这种波动以小时为单位出现。

#### 6. 评判困难的证据

- 流程自报通过，验证报告里有失败和跳过（见第 4 小节）。
- 第 1 次运行自己发现了三处"检查看起来通过、实际没有检查到"的地方：编译检查第一轮只编入了 4 个源文件；骨架审计把 ArkTS 编译器要求的写法判定成残留代码；占位登记表被 6 处空行切成 7 段，7 行更新没有生效，也没有报错。
- 本机两次运行都没有执行视觉检查。更早两次 DevEco 运行共产生约 17,300 次工具结果，送进模型的图片只有 7 张，全部是应用图标。

#### 7. 耦合的证据（更早的 omp 移植版运行记录）

- 一次只修改 5 个字段的计划修订，让 10 个执行包全部失效，需要逐个重新登记。
- 修改一个文件里的一条注释，改变了这个文件的摘要，依赖它的另一个功能包被判定为依赖无效。

### 由此引出贪心链

拿整条流程迭代技能有三个问题：

1. **慢**：按 A2H-RepoBench 的规模，一次运行 12 到 44 小时。比较两个技能版本、每个版本运行 8 次，就是 16 次运行，合计 190 到 700 小时。
2. **噪声大**：上游阶段的波动会传到下游。修改 plan 技能之后，比较结果里混着 spec 阶段的波动。
3. **无法定位**：最终结论是一个总判断，看不出是哪个阶段、哪个技能出了问题。

## 四、贪心链：把长流程切成可以比较的单元

### motivation

上一节的三个问题，都来自"整条流程只在结尾判定一次"。贪心链把比较对象缩小到一个单元：同一个起点、同一段提示、同一组规则。单元越小，一次比较越快，失败越容易定位。

### design

1. **按技能自己的边界切分单元。** 每个单元只承诺一小段工作，有自己的完成标记。
2. **每个单元从一份冻结的起点快照开始。** 起点是上一个单元选出的工程树。
3. **从同一个起点并行运行 n 份候选。** n 从 1 开始，判定不合格才按倍率增加。
4. **用同一组规则逐份判定。** 规则清单转成 DoG 图，每条规则一个独立的判定会话。
5. **选择最好的一份作为下一个单元的起点。** 每一步只选当前最好的一份，不回头修改前面的选择，所以叫"贪心"。
6. **全部候选都不合格就停止。** 链条停下报告，不从不合格的候选里挑"相对最好"的。
7. **用对照实验检查贪心是否有收益。** 和整条运行、随机选择比较。

### spec

#### 1. 单元

- 本机：整条迁移切成 56 个单元。顺序是 spec → plan → 执行阶段的各个批次、各个基础包、每个 slice 的四个步骤（9 个 slice × 4 = 36 个单元）→ 收尾阶段的循环 → 终态编译 → 验证 → 验证汇总 → 复盘。
- kp3：57 个单元，单元表写在链条脚本里。

#### 2. 一个单元内部

| 规则 | 本机 | kp3 |
|---|---|---|
| 起始份数 | spec、plan 两级最早固定 8 份；之后一律从 1 份开始 | 57 个单元里 50 个从 1 份开始，5 个从 2 份，2 个从 4 份 |
| 不合格时 | 份数乘以 2 | 份数乘以 2 |
| 份数上限 | 收尾类 4、验证类 3、其他 2 | 收尾类 16、验证类 12、其他 8 |
| 单元累计尝试上限 | 无 | 开始时 40，2026-10-17 改为 8（只对之后启动的进程生效） |
| 全部不合格 | 停止并报告 | 停止该链并告警 |

#### 3. 一份候选内部（kp3 的实现）

- 一份候选最多 3 个回合，每个回合调用一次运行外壳，单回合超时 5,400 秒。第一回合用原任务，后续回合在同一个会话里发续跑提示。
- 收尾判定：dsh 要求本回合开始之后有完成信号（由 `work_complete` 工具写入）；其他外壳以进程结束为准。3 个回合仍未收尾，这份候选失败。
- 网关故障不计入失败：事件里出现 `No available providers`、`rate limit`、`503 Service` 这类文本时，本回合不计数，等待 300 秒重试同一回合，最多 36 次。
- 额度或容量失败的候选移出，不判定，也不占份数。
- 判定器忙或不可用：重试后仍不可用，就停止整条链，不把候选判定为不合格。

#### 4. 判定器怎样工作

1. 规则清单：每个单元一份，每条规则写明编号、等级、要求、证据形态。等级分两种：必过规则（失败即淘汰）和普通规则（失败只计入失败条数）。
2. 转成 DoG 图：每条规则一个叶子；必过规则的失败标为致命；根节点要求全部通过。
3. 组装冻结证据目录：会话原文、产物差异、运行摘要、工程树的写时复制克隆。超过 64 MiB 上限时，写明取舍。
4. 每条规则一个 `omp --mode rpc` 判定会话。判定只看冻结证据，代理在会话里的自述不算证据；证据不足记为无法观测。
5. 结果写入 `judge.json`。规则清单没有变化时复用旧判定。

#### 5. 合格与选择

- 合格：没有必过规则违背、没有失败、没有无法观测，并且判定进程正常退出。全部无法观测是"判定没有发生"，不算合格。
- 选择顺序：必过规则违背数最少 → 普通规则通过条数最多 → 墙钟时间最短。kp3 的脚本只实现了前两项，平手时按候选目录名的顺序。

#### 6. 判定结果的三种读法

同一份判定，例如 S1、S2、S4 通过，S3 失败，S5 无法观测：

- 二值：只看根节点。S3 是必过规则，整份就不通过。
- 不加权：通过条数除以规则总条数，3/5 = 0.60。
- 加权：先看必过规则，有一条必过规则失败就直接淘汰；必过规则全部通过，再按普通规则的通过条数排序。

#### 7. 本机实验：贪心链与整条运行对照（2026-10-08 至 10-09）

| 口径 | 贪心链（逐级选择） | 整条运行（不做中间选择） |
|---|---|---|
| 候选份数 / 单元数 | 84 / 56 | 2 / 1 |
| 运行费用 | $44.62 | $13.30 |
| 判定费用 | $15.28 | $0.72 |
| 合计 | $59.90 | $14.02 |
| 候选墙钟累计 | 19.5 小时 | 10.6 小时 |
| 规则判定：通过 / 失败 / 无法观测 | 328 / 4 / 11 | 10 / 0 / 0 |
| 必过规则违背 | 2 | 0 |
| 末端产物（同一组 W1–W5 规则） | W2 失败（必过规则） | 全部通过 |

- **一次比较的开销变小**：每份候选的墙钟中位数约 12 分钟，最长 48 分钟；tokens 中位数约 2 千万（含缓存）。整条运行一次是 3 到 7.6 小时、约 8 亿 tokens。
- **规则没有区分度时，多运行的份数是浪费**：最早 spec、plan 两级各运行 8 份，80 条判定全部通过，胜者实际由排序和墙钟决定。之后改为从 1 份开始、不合格才增加，同级费用降到约 1/7。
- **判定费用不可忽略**：判定费用约占贪心链总费用的四分之一。
- **末端 W2 失败的原因在实验设计**：收尾阶段的循环，贪心链只给了 2 轮（两个单元）；整条运行在一个会话里运行了 7 轮，直到没有需要修改的发现。每个单元运行几份、循环运行几轮，必须事先确定。
- **两种运行方式在真实缺陷上一致**：验证报告的 CHECK-2 都判定为失败（bundleName、vendor 仍是脚手架默认值），都如实登记。

#### 8. kp3：七个运行外壳在同一套判定下（2026-10-15 至 10-17）

模型都是 DeepSeek Flash（各外壳的模型名写法不同，例如 `deepseek/deepseek-flash`、`openai/deepseek-flash`），每个外壳一条 57 个单元的链。

| 外壳 | 完成单元 | 候选份数 | 规则判定：通过 / 失败 / 无法观测 | 必过规则违背 | 结束方式 |
|---|---|---|---|---|---|
| dsh | 57/57 | 95 | 352 / 12 / 29 | 8 | 走完 |
| miniswe | 57/57 | 87 | 344 / 11 / 6 | 2 | 走完 |
| omp | 57/57 | 85 | 322 / 14 / 14 | 4 | 走完 |
| codex | 55/57 | 133 | 465 / 37 / 52 | 27 | retrospect 单元 8 份候选都不合格 |
| pi | 55/57 | 128（118 份有判定） | 384 / 65 / 43 | 34 | retrospect 单元 8 份候选都不合格 |
| claude | 3/57 | 19（累计尝试 47） | 39 / 17 / 29 | 17 | stage1-batch2 没有合格候选；决策记录写"拒绝执行批次" |
| deveco | 2/57 | 10 | 25 / 11 / 6 | 6 | stage1-batch1 没有合格候选；决策记录写"慢且差一条" |

- 2026-10-17，因 token 开销停止全部七条链。
- 设备检查单元在 2026-10-17 从链中移除：kp3 上的设备隧道没有监听，环境不可用。这七条链的结果里没有设备上的视觉检查。

#### 9. 代价与局限

- 贪心是局部选择，不保证全局最好。要判断贪心是否有收益，需要三种对照：整条运行（本机已做）、随机选择的链（还没有运行）、每一级候选的判定分布。
- 单元切分会丢失跨单元的上下文。收尾循环这类需要多轮的阶段，轮数必须事先定好。
- 判定费用和运行费用同量级，规则清单越长越贵。
- 规则本身可能写错。本机遇到过一次：规则写"不许修改计划目录"，把套件契约要求新增的文件判定成越界，一份合格候选被判定为不合格。写规则之前，要先和套件契约对读。

## 五、DDoG：让检查图随真实失败增长

### motivation

DoG 图写久了会膨胀。本机贪心链里，spec、plan 两级的 80 条判定全部通过：这些规则几乎从不失败，每次运行却都要付判定费用，也说不清哪些节点真正有用。

作者原话："DoG图也开始腐化，无限膨胀了。但是很多时候有一些节点几乎从来就不会错，问题是我怎么判断会不会错？"

DDoG（Dynamic DoG）换了一种做法：不一次写出整张大图，从根节点开始，用真实例子和真实交付物反复检查，只让真实失败生成新节点。

### design

1. **四种节点**：根、候选、正式、退休。根来自用户指令，候选来自真实失败。
2. **父节点在同一个会话里判定候选和退休子节点。** 候选不单独启动判定会话，节省 tokens。
3. **父节点必须从自己的定义重新推导失败方式。** 不能只看已有子节点；发现没有覆盖的失败方式，就提交新候选。
4. **状态由运行层按阈值迁移，只向前变化。** 判定记录只追加，不覆盖。父节点不能自己决定转正或退休。
5. **三个入口**：从零开始定义根；从真实例子生成候选；用真实交付物判定。已有的 DoG 图可以直接导入。
6. **案例分两种来源**：生产环境的反馈价值最高；模拟生成的案例价值低。两种不能混在一起下真实结论。
7. **prompt 只有一个来源。** 运行时只注入共同原则和当前任务两段。

### spec

#### 1. 节点

| 节点 | 来源 | 怎样判定 |
|---|---|---|
| 根 | 用户指令，写成一句话定义 | 独立会话 |
| 候选 | 真实例子或交付物里出现、现有子节点没有覆盖的失败方式 | 由父节点在同一会话里判定 |
| 正式 | 候选达到转正条件 | 独立会话 |
| 退休 | 正式节点达到退休条件 | 回到父节点的会话里判定 |

#### 2. 生命周期阈值

- 候选转正式：失败次数超过 2 次，并且失败率超过 20%。
- 正式开始退休评估：通过率超过 90%。
- 正式转退休：至少有 5 个过往失败案例；父节点对每个案例给出判定；父项和子项判定的一致性超过 80%（用交叉熵计算，至少 5 次）。

#### 3. 父节点一次判定要做的事

1. 先判定自己，再判定每个直接候选和退休子节点。
2. 判定完现有子节点后，从自己的定义出发，重新推导所有失败方式；用形式逻辑和经院哲学的方式穷举，不用分类标签。
3. 检查每个失败方式是否已经被候选、正式、退休或更深的子节点覆盖。
4. 本次交付物命中了没有覆盖的失败方式，就提交新候选：一句话定义，加交付物的原文证据；同时父节点必须判定为失败。
5. 过往失败案例按顺序逐个给出判定，供运行层计算退休一致性。

#### 4. 三个入口

| 入口 | 由谁运行 | 输入 | 输出 | 图的变化 |
|---|---|---|---|---|
| `init`（从零开始） | 苏格拉底式根定义 agent | 用户指令文件 | 一句话根定义 | 创建根节点；不合格时修正一次 |
| `expand`（生成候选） | 生成方 agent | 父节点、现有子节点、真实例子、来源 | 候选树 | 追加候选；不判定、不转正、不退休 |
| `run`（生产判定） | 父项判定 agent；根和每个正式节点各一个会话 | 父节点、候选、正式与退休子节点、过往失败、交付物 | 各项判定、新候选、退休判定 | 追加判定和新候选；运行层按阈值迁移状态 |

#### 5. 定义与追溯

- 每个节点是一句话定义，只有一个句末标点；写被判断的性质，不写怎么做；用词典能查到的词。
- 根定义的检查：一句话；至少 20 个字符；包含定义谓语（是、指、作为、即、意味着）；与用户指令至少共享一个两字以上的片段。用户认可的例子："学术论文是一种以可复核证据让读者相信并采用作者核心判断的论证文本。"
- 根定义是复合命题：每个合取项至少要有一个候选覆盖。
- 每个候选都能追溯到一个真实例子：`exampleIndex` 是例子编号，`trigger` 是该行原文摘录。
- 不预设总层数，不要求补全同一层，只保留有真实例子支持的路径。

#### 6. 导入已有的 DoG 图

- 导入时校验根、层级、父链、状态、是否有环。根定义必须是功能句。
- 旧判定历史保留；没有历史的节点从"没有结果"开始，不默认通过或失败。
- 旧节点的文字作为数据进入节点定义和案例，不进入 system prompt。
- 很大的平铺静态图导入后，第一轮仍然要判定很多直接子项；成本只能随退休逐步下降。

#### 7. prompt 怎样注入

| 入口 | 注入内容 | 输出工具 |
|---|---|---|
| `init` | 共同原则 + 根定义任务 | `ddog_submit_root` |
| `expand` | 共同原则 + 生成候选任务 | `ddog_submit_candidates` |
| `run` | 共同原则 + 父项判定任务 | `ddog_submit_parent_verdict` |
| 状态迁移 | 不加载 prompt | 无 |

一个节点 agent 只拿一个角色的 prompt，只看到一个输出工具。节点定义、父链、候选、交付物、案例都放在 user message 里作为数据。

#### 8. 已知边界

- 正式子节点的失败，目前不会自动并入根节点的判定结果。
- 根节点合取项的覆盖检查，只检查"每个条件至少有一个候选"，不保证候选在语义上真的检查了这个条件。
- 退休路径有单元测试，还没有端到端的真实运行证据。
- 模型判定有随机性。契约保证结构、记录和状态迁移，不保证同一交付物每次得到相同判定。

## 六、技能自迭代：只修改归因到技能文本的失败

### motivation

hmigbot 的技能文本一直在增长。作者原话："我苦恼于skills无限增长，又臭又长，开始腐化，效率低下的问题。"增长的原因是："模型容易让skills无限增长，原因是因为不知道其他模型使用的时候是否会犯错，容易把一些明明实践中从来没犯过的错也写进去，属于是废话。模型在读取skills的时候，一长就容易丧失重点。另外也会造成多重truths。"

所以技能自迭代有三条要求：只根据真实发生的失败修改技能；修改前后可以比较；修改后的文本本身也要合格。

### design

```text
基线判定 → 失败归因 → 修改技能 → 技能质量图检查
  → 从同一份快照重新运行至少 8 轮 → 比较通过率
  → 从前置单元运行到后置单元做端到端检查 → 保留或回退
```

约定：

- 规则逐条单独判定；无法观测不算通过。
- 只修改归因到技能文本的失败；环境、模型、判定器的问题先修复对应部分。
- 一次只修改一个技能，或一组紧密相关的规则，修改后才能归因。

### spec

#### 1. 五条编写原则（作者原话整理）

1. **复用模型已经掌握的知识。** 已有业界规范的要求直接引用，不重新解释。例如不必写一大段文字解释 `ls -a`、`ls -h`，直接让模型运行 `ls --help`：既让模型进入熟悉的规范环境，也避免出现多个事实来源。补充规则：模型的先验可能过期，`--help` 也可能不存在或版本不一致；复用之前，先确认权威来源在当前环境里可用、版本一致。
2. **单一事实来源。** 多个不同的事实来源是腐化最常见、也最容易让 agent 出错的形式。
3. **人和模型脱离上下文都看得懂。** 模型会按自己的上下文写出一段文字，并以为别的模型也看得懂；没有这段上下文的读者往往看不懂。
4. **抽象。** 意图优先于行动，常见情况优先于罕见情况和边界情况；设立不同的抽象层，需要时再读取。
5. **效率。** 借鉴缓存机制和人类实践，把模型容易犯的错误整理成 FAQ，并在模型更新时定期维护。

#### 2. 通过率口径

- 通过率 = 判定通过的规则条数 ÷ 规则总条数。无法观测不算通过。
- 一律逐条单独判定。原因：同一份 spec 候选，五条规则一次判定时是 5/5 通过，逐条判定时 S1 失败；同一份 retrospect 候选，一次判定全部通过，逐条判定时 R4 失败。

#### 3. 失败归因：四类

| 类别 | 本实验里的例子 | 处理 |
|---|---|---|
| 环境 | 第一次改写后试运行，71 秒就结束了：容器里缺少 Android 工程目录，工程路径和配置不一致，流程的启动检查直接停止 | 修复容器挂载，重新运行 |
| 模型或运行外壳 | kp3 上 claude 外壳拒绝执行批次，链条停在第 3 个单元 | 不修改技能 |
| 判定器 | spec 的 S2、S3 和 plan 的 P1、P4，在 300 秒内没有提交判决 | 记为无法观测，不当作技能失败的证据 |
| 技能文本 | 见下一小节的三个单元 | 修改技能 |

#### 4. 基线与修改

| 单元 | 失败规则 | 证据 | 归因 | 修改 | 基线通过率 | 目标（相对 +10%） |
|---|---|---|---|---|---|---|
| spec | S1 | `ui-manifest.md` 存在；`feature-index.md` 缺失 | 技能要求用户在 Gate B 确认；无人值守时停在 Gate B，没有进入下一阶段 | 增加无人值守的审批路径；完成标记两个文件缺一不得结束 | 2/5 = 40% | 44% |
| plan | P2 | `spec/baseline/plans/` 目录不存在，`feature-plan.md` 读取失败 | 技能没有先建立计划目录；四个完成标记缺一仍然继续 | 生成计划前先建目录；四个完成标记缺一即报告 `PROCESS_BLOCKED` | 2/5 = 40% | 44% |
| retrospect | R4 | 报告里的频次、级联数等数字，在迁移报告和阶段记录里找不到来源 | 报告模板没有要求数字附来源 | 每个数字附"来源：相对路径:行号或字段"；末尾加数字对账表；无法追溯写 `UNVERIFIED` | 3/4 = 75% | 82.5% |

基线候选来自 kp3 上 omp 外壳的链；三处修改都只增加一到两句约束，没有复制已有内容。

#### 5. 技能质量图

- 用五条编写原则建一张 DDoG 图，每条原则是一个候选节点，判定修改后的技能文本；必过项全部通过，修改才能进入重新运行。
- omp-dog 另有一张静态的技能质量图，五个质量轴：触发与范围、单一事实来源、脱离作者上下文、分层与长度、相对基线的收益。确定性检查（frontmatter、行数、绝对路径、凭据、引用关系）由脚本完成，语义判断由 agent 叶子完成。

#### 6. 验收口径

- 至少 3 个单元。
- 每个单元从同一份快照重新运行至少 8 轮；每轮独立判定，不取最好的一轮。
- 修改后的平均通过率相对基线提升至少 10%。
- 对每个修改过的技能，从前置单元运行到后置单元，确认没有引入新的失败。
- 开销估计：三个单元每份候选分别约 1,470 万、940 万、560 万 tokens（含缓存）；每单元 8 轮、共 3 个单元，约 2.4 亿 tokens，还没有计入判定。

#### 7. 当前状态（2026-10-19）

- 三个单元的基线判定已完成。
- spec 单元的改写后重新运行正在 kp3 上进行；plan、retrospect 还没有开始；技能质量图的判定正在运行。
- 还没有改写后的通过率。演讲时这一节只能讲方法和基线。

#### 8. 已有工作与差别

截至 2026-10-19，我们查找了 18 项技能自迭代或相关工作，其中 17 项能读到正文（Skill² 的 OpenReview 页面无法访问）。挑出有代表性的几项：

| 工作 | 判定器 | 最长任务 | 失败归因 | 技能文本质量控制 | 接受修改的统计口径 |
|---|---|---|---|---|---|
| CoEvoSkills（2604.01687） | 独立 LLM 会话生成测试 + 隐藏的标准答案测试，三方信息隔离 | 单任务超时 2 小时，实际墙钟未报告 | 只指出覆盖缺口，不分类 | 无长度控制 | 5 次独立运行，均值与标准差 |
| SkillOpt（2605.23904） | 基准自带评分；独立优化模型；留出集严格提升才接受 | 短程（ALFWorld 每回合 50 步） | 只分析成功与失败轨迹 | 修改幅度预算、去重、冲突合并 | 单次训练 |
| WikiSkill（2608.27454） | 基准评分 + 验证集，性能下降就回滚 | 未报告墙钟，非超长程 | 无显式归因 | 提示词要求简洁 | 3 次完整演化，配对 bootstrap 检验，p < 0.05 |
| SkillHone（2606.08671，腾讯） | 评估方和优化方权限隔离，优化方只看脱敏报告 | 多步检索任务，未报告墙钟 | 记录诊断，无分类 | 回归测试、按范围回退 | 未报告重复次数 |
| VeriSkill（2607.27733） | 程序验证器 + 人工验证的参考解 | 程序验证任务，非超长程 | 四类：任务不可满足、证明器能力限制、技能未被遵循、技能知识缺口；只用后两类修改技能 | 修改要写适用条件与不适用场景 | 3 次平均 |
| ECAT（2608.09273，华为） | 独立判别器，14 个维度加权的 Code Entropy；生成器和判别器每轮重新创建 | 整个应用迁移，12–44 小时 | 定位高熵区域，无责任分类 | 记忆树合并冗余条目 | 3 次独立运行，均值与标准差 |
| 本项目 | DoG/DDoG 结构化图；每条规则独立会话、冻结证据、允许无法判定 | 整个应用迁移；目前只有 Jetsnack 冒烟测试的完整运行，单次 3–7.6 小时 | 四类：环境、模型、判定器、技能文本；只用最后一类修改技能 | 五条编写原则建成的 DDoG 质量图 | 同一快照至少 8 轮，相对提升至少 10%；还没有显著性检验 |

结论：

- 已有工作各自在一两个方面做得很好：SkillHone 的权限隔离、VeriSkill 的失败归因、WikiSkill 的统计检验、SkillOpt 的工程完成度、ECAT 的超长程任务。
- 在我们核实的范围里，没有找到同时覆盖五项的工作：结构化、可拆分的价值判定器；超长程任务；失败归因；技能文本质量门；多轮统计验收。也没有工作把非形式化的价值判断拆成有向无环图后逐节点判定。
- 已核实正文的 14 项工作，没有一项报告判定器与人类判断的一致性。本项目目前也没有这组数据。
- 本项目要做的，是把这五项放进同一条流程，并且每一项都按生产运行的要求实现：kp3 容器内运行；omp RPC 驱动；两个 key 负载均衡；网关故障不计入失败；判定器不可用就停止，不误判；实时看板和看门狗发现卡住的运行；记账覆盖全部子代理会话。

## 七、边界与时间线

### 这套机制保证什么

- 每个判定都绑定冻结证据和判据身份，别人可以复核。
- 无法判定、复用的旧结果、被取消的运行，都如实标注，不报告成通过。
- 只修改归因到技能文本的失败；修改前后使用同一快照、同一模型、同一组规则。

### 这套机制不保证什么

- 判定的确定性：同一对象多次判定可能不同；没有投票，也没有自动复检。
- 与人类判断一致：还没有测量。
- 全局最优：贪心链是局部选择；随机选择的对照链还没有运行。
- 视觉质量：kp3 上没有可用的设备，链里的设备检查单元已经移除；缺少视觉证据时只能记为无法观测。
- 统计显著：8 轮只能降低偶然波动，目前没有置信区间。
