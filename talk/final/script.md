## 读法

每个场景一节，格式固定：

- 第一行 `## \`场景 id\` · 计划时长`；
- `标题：` 是页眉标题，`副标题：` 是页眉下面一句；
- 每一步是一条编号：`〔字幕〕` 是屏幕下方那一句（写「（无）」表示这一步不显示字幕条），`〔画面〕` 是画面说明，其后缩进的段落是讲稿。

听众：只听过 Agent 这个概念、不了解它怎么工作、也不了解目前怎么评测它的人。所以每个非通用术语第一次出现时当场解释，名词表在附录 B。

组织方式：论文式。先用摘要讲完现状、关键判断、我们的实现、最终结果；再分章展开。每一章开头有一页章节页，页眉左上角始终显示当前所在的章。主题聚焦贪心链，以及找出指令遵循被违反的地方；自迭代少讲。

## `abstract` · 2:00

标题：摘要
副标题：现状、关键判断、我们的实现、最终结果

1. 〔字幕〕**现状**：skills 控制超长程工作流，效果只能靠端到端判断
   〔画面〕四格画面的左上格亮起：一条长流程，五个阶段方块依次点亮，末端一个问号。
   先用两分钟概述全部内容。现状：hmigbot 用 74 个 skills 组织 Android 应用向鸿蒙的整体迁移。一次运行要几个小时，随机性很大，最终效果只能靠端到端判断。
2. 〔字幕〕**关键判断**：指令遵循是评判 skills 的重要一环，需要新的判定方法
   〔画面〕右上格：一份 skill 文件，旁边的判定标记在“遵循”和“不遵循”之间来回切换。

3. 〔字幕〕**我们的实现**：贪心链逐单元筛选，判定器逐条定位违反
   〔画面〕左下格：spec 单元的 4 份候选排成 4 行，5 条规则按列展开；判定器逐条判定，第 3 份在 S1、S2、S3、S5 上标红，第 4 份五条全部通过并标为 top-1，箭头指向下一单元 plan；底部是三种判词的颜色图例，右下角只留一个很小的自迭代去向标记。
   我们的实现分两层。判定器 DoG 与 DDoG：每条规则交给一个独立的 LLM 会话判定，结论是通过、不通过或无法判定。贪心链：把整条流程切成 57 个单元，每个单元并行跑几份候选，判定器逐条判定，违反的规则标红；没有必过规则违反、通过条数最多的一份，作为下一个单元的起点。定位出来的问题，最后才交给自迭代去改 skills。
4. 〔字幕〕**最终结果**：违反集中在 retrospect、plan、verify 三个阶段
   〔画面〕右下格：七个阶段的规则违反率横向条形图，按违反率从高到低排列；前三行加红底，标出违反率最高的三个阶段；底部注明统计口径和 145 条无法判定。
   结果：五条贪心链一共 2,170 条规则判定，整体违反率 8.2%。违反集中在三个阶段：retrospect 26.2%、plan 25.5%、verify 22.4%，其余四个阶段都低于 7%。另有 145 条无法判定，单独列出，不算进违反率。这三个阶段，就是贪心链定位到的指令遵循度最低的地方。

## `words` · 1:00

标题：先认识四个词
副标题：LLM、Agent、skill、harness

1. 〔字幕〕**LLM**：读入一段文字，接着写出下一段文字的模型
   〔画面〕一个模型方块；左边一行行文字流进去，右边一行行文字流出来。
   先认识四个词。LLM 是大语言模型：给它一段文字，它接着往下写。这一次交给它的全部文字，叫上下文。
2. 〔字幕〕**Agent**：LLM 在循环里调用工具、读结果、再决定下一步
   〔画面〕模型方块外画出一个循环：模型 → 工具（读文件、跑命令）→ 结果 → 模型；循环上的光点一直转。
   Agent 是把 LLM 放进一个循环：模型决定调用什么工具，比如读文件、跑命令；工具的结果放回上下文，模型再决定下一步。一次迁移任务，这个循环要重复几千次。
3. 〔字幕〕**skill**：一个文件夹，写着某一类任务该怎么做
   〔画面〕一个文件夹打开，里面是 SKILL.md、参考文档、脚本三样；SKILL.md 飞进模型的上下文。
   skill 是一个文件夹：主文件 SKILL.md 写这类任务怎么做，旁边放参考文档和脚本。Agent 遇到这类任务时把它读进上下文，按它工作。
4. 〔字幕〕**harness**：驱动这个循环的程序，例如 omp、Claude Code、Codex
   〔画面〕循环外面套一层外框，外框上依次出现 omp、Claude Code、Codex 等名字。
   harness 是驱动这个循环的程序，负责把工具接给模型、把结果放回上下文。同一个模型放进不同的 harness，表现差别很大，后面会看到数字。

## `hmigbot` · 2:00

标题：hmigbot：一个超长程任务
副标题：用 skills 控制工作流，把 Android 应用整体迁移到鸿蒙

   〔画面〕五个阶段方块从左到右排开：spec、plan、execute、verify、retrospect；每个方块下面挂出几张 skill 卡片；顶部一行“skills 控制工作流”，右侧两个标签“74 个 skills”“11 类子代理”。

## `judgments` · 2:00

标题：七条关键判断

## `ci` · 1:15

标题：形式化验证与非形式化验证
副标题：能写成程序判定的交给 CI；写不成程序的，需要另一种检查

1. 〔字幕〕形式化验证：判定规则能写成程序，同样的输入每次得到同样的结果
   〔画面〕左边一条 CI 流水线：编译 → 测试 → 静态检查，三个绿灯依次亮起；一份代码提交沿流水线流过去。

2. 〔字幕〕非形式化验证：“这篇论文值得相信吗”“这次迁移有没有按 skills 做”

3. 〔字幕〕DoG 只处理非形式化目标；先拆成抽象层，再拆到叶子；其中一部分检查可以交给脚本

   DoG 只处理非形式化目标。它先把目标拆成一层抽象节点，每个节点还可以继续往下拆，直到叶子。一部分检查可以用脚本完成；如果一整个分支都能写成程序，那一支就交给普通测试。DoG 只判定产物，不负责生成产物。

## `dog` · 3:45

标题：DoG：把一句模糊的目标拆成一张图
副标题：DAG of Goals，由目标组成的有向无环图

1. 〔字幕〕起点是一句定义不清的话：“我要一篇好论文”
   〔画面〕一句话浮在中间，“好”字闪烁；周围冒出几个问号：“AI 味轻？”“不过度防御？”“读得懂？”；底部一个琥珀色标签“缺少验收标准”，一条小注解释 RLHF。
   DoG 的起点是一句定义不清的目标，比如“我要一篇好论文”。RLHF 是训练时按人类偏好打分来调整模型的方法；模型在这个阶段已经学过一般人心中的“好”，所以这句话没有给它新的信息。你心里的标准，可能是 AI 味轻，可能是不过度防御，而你自己一开始也说不清。缺的是验收标准。
2. 〔字幕〕DAG：节点加箭头，顺着箭头走永远回不到出发的节点
   〔画面〕几个点用箭头连起来；一条想从下往上绕回起点的箭头变红、消失。
   DoG 是 DAG of Goals，由目标组成的有向无环图。图由节点和箭头组成；有向，是箭头有方向；无环，是顺着箭头走，永远回不到出发的那个节点。
3. 〔字幕〕根节点保留用户原意；第一层是它可能失败的方式
   〔画面〕根节点“文章质量门禁”向下长出三个子节点：“内容质量（四维）”是组合节点，“模板词提示（辅助）”和“文件存在且非空”已经是可以直接判定的叶子；左侧短注“抽象层：父目标在下一层的失败方式”。
   根节点写用户的原意，允许模糊。往下拆的方法是问：这个目标可能怎样失败。第一层拆出三个子节点：内容质量（四维）还要继续往下拆；模板词提示和文件存在且非空已经足够单一，可以直接交给判据。抽象层记录的是父目标在下一层的失败方式。
4. 〔字幕〕内容质量继续拆成四片叶子；叶子可以用脚本或独立 LLM 会话判定
   〔画面〕“内容质量（四维）”下长出四片叶子：AI-slop 味、信息密度与趣味、易懂、人类质感，都标“LLM 判定”；根下的两片程序叶子标“脚本”；一个独立判定会话的窗口连到 LLM 叶子，交回一张判决卡。
   内容质量（四维）是组合节点，继续按失败方式往下拆，得到四片叶子；每一片叶子只判定一件事。叶子有两种判据。程序判据是一个脚本，读冻结的产物，输出通过、不通过或无法判定。agentic 判据是一句自然语言，交给一个独立的 LLM 会话；这个会话必须交回一次判决和证据。
5. 〔字幕〕不只叶子有判定：这张图的根与组合节点都有自己的整体断言
   〔画面〕根与内容质量各出现“整体断言”标记；四片叶子全部变绿“通过”，内容质量的整体断言发现“信息密度高，但读不懂”，内容质量与根依次变红“不通过”。
   不只叶子有判定。这张图里，根节点和内容质量都有自己的整体断言；组合节点的整体断言在子树全部结算之后执行，只能把结果往下调，不能把失败改成通过。举一个具体例子：四片叶子都通过了，内容质量的整体断言把四个维度合起来看，发现“信息密度高，但读不懂”这组结果互相矛盾；这个问题没有对应的叶子，仍然被父节点抓到，内容质量判定为不通过，根也随之不通过。这样，抽象层被展开时没有写进叶子的方面，仍然会在上层被检查到。
6. 〔字幕〕失败沿边向上传播：必过项失败，父节点不通过；可容忍项失败，只算部分问题
   〔画面〕先复位到全部通过；可容忍的“模板词提示（辅助）”变红“不通过”，根记为“部分”；随后必过的“AI-slop 味”变红，内容质量与根依次“不通过”；底部规则条解释 fatal 与 tolerable。
   结果从叶子往上传。每条边记录失败的影响：fatal，失败一直往上传，父节点不通过；tolerable，只算部分问题。可容忍的模板词提示失败，根记为部分问题；必过的 AI-slop 味失败，内容质量这一层先不通过，再往上传到根。中间层的判定和叶子一样参与传播。
7. 〔字幕〕无法判定时如实报告，逐层向上传，交给人处理
   〔画面〕一片叶子变成琥珀色“无法判定”，内容质量这一层也变成“无法判定”，根变成“需要重新规划”，一条粉色线连到人像图标。
   最后一条纪律：无法判定，就如实报告无法判定。脚本出错、会话超时、没有交回判决，都记为无法判定。无法判定会沿层往上传：叶子无法判定，父节点也无法判定，根节点变成需要重新规划，交给人处理，不会被当成通过。

   〔画面〕改写后的 skill 卡片进入质量门禁（六个检查项依次变绿）；然后从同一个冻结起点复制出 8 份重跑，结果点排成一行。

## `gate` · 1:45

标题：质量门禁：防止 skills 越改越腐化
副标题：五条原则写成六条可以判定的规则

1. 〔字幕〕让模型改 skills，它容易越写越长，读的时候丢掉重点
   〔画面〕一个 skill 文件越拉越长，相同的段落重复出现，颜色逐渐变暗。
   为什么需要质量门禁？让模型改 skills，它容易越写越长：模型不知道别的模型用的时候会犯什么错，就把从没发生过的错误也写进去；skills 一长，读的时候就丢掉重点，还会出现几处互相矛盾的说法。
2. 〔字幕〕五条原则：复用模型已有知识、单一来源、脱离上下文也清晰、抽象、效率
   〔画面〕五条原则依次出现，每条一个短标题，下方是原话的第一句。
   所以我给 skills 定了五条原则。第一，尽量复用模型已有的知识，比如直接让模型运行 ls --help，不必在 skills 里解释 ls -a。第二，同一个事实只有一处来源；多处说法不一致，是腐化最常见、也最容易让 Agent 出错的形式。第三，人和模型脱离上下文也能读懂。第四，分抽象层：意图优先于具体操作，常见情况优先于边界情况，细节需要时再读取。第五，效率：把模型常犯的错误整理成 FAQ，并在模型更新时维护。
3. 〔字幕〕写成一张质量门禁图：六条必过规则，每条一个独立会话判定
   〔画面〕五条原则各自连线到六个检查项：single-truth、context-independent、abstraction、reuse-model-knowledge、no-metaphor、faq；每个检查项旁边弹出一个独立的判定会话。
   这五条原则写成一张 DoG 图，六条必过规则：单一来源，脱离作者上下文，抽象，复用模型知识，不用比喻，FAQ。每条规则一个独立会话，去判定改写后的 skills。
4. 〔字幕〕改写后，三份 skills 都变短了
   〔画面〕三对长短条，长条缩成短条；plan 旁边的文件数从 13 变成 2。
   改写后，spec 从 773 行减到 166 行，plan 从 475 行减到 177 行、文件从 13 个减到 2 个，retrospect 从 196 行减到 152 行。篇幅变短的代价，在讨论章说明。
