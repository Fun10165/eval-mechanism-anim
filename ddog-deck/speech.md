# 从指令违反到可复核的自迭代

约 35 分钟。下面按场景顺序写，画面动作放在括号里，正文是可以直接照读的讲稿。

## 0:00–3:00 介绍：先确认有没有按规则走

（画面：封面 → 最小例子）

今天我想讲一个很具体的问题：长程任务里，Agent 没有按技能文本走，我们还能不能知道自己在测评什么。

先交代三个前提。第一，迁移任务有一套技能文本，Agent 按它工作。第二，同一份配置重复运行会有随机差异。第三，判定可以放在独立的只读会话里做，不和产出会话混在一起。

我的判断是：先定位指令违反，再固定比较对象，再让判定可复核，只改归因到技能的部分，只重跑变化的部分。这句话我会在最后原样收住。

为什么这件事难？看一个最小例子。把 Jetsnack 从 Android 迁移到鸿蒙，技能文本规定五个阶段：读需求、列计划、写代码、自检、打包。候选 A 每一步都按技能文本走。候选 B 在列计划这一步跳过了，直接去写代码。最后两份都能打包，甚至都能打开。只看结果，B 看起来也不错。

可是 B 的包已经离开了技能文本要求的那条路。拿它和 A 比，比较对象已经不同。我们不知道自己在评测什么：是在评测技能文本要求的那条路，还是在评测一个已经偏离要求的东西。

所以第一件事是先确认有没有按规则走，打分可以稍后再谈。这就是今天整条主线的起点。

## 3:00–5:00 普通 CI 看不到过程

（画面：普通 CI 与 Agent 工作检查）

普通 CI 很擅长回答程序能不能跑：编译、测试、静态检查，结果确定，失败能定位到文件和行号。可是它看不到 Agent 的过程。一个 Agent 可能跳过计划、自己发明做法、结论没有证据，最后代码仍然能编译。普通 CI 会亮绿灯。

这里需要换一类检查。我们要把过程有没有按规则走拆成一条条可以核对的小判断，再把产物、会话和证据放在一起看。这个检查不是一条命令能完成的，它需要证据，也需要判定。

有了这个判断，贪心链才有意义。贪心链要让每一次比较都有确定的起点和确定的终点；多跑几遍只是手段。

## 5:00–9:00 贪心链：先把比较对象固定住

（画面：57 个单元 → 冻结起点 → 复制 → 判定 → top-1）

把整条迁移流程切成 57 个单元。一个单元是流程里可以单独开始、单独结束的一小段。每个单元都有一个冻结的起点，通常是上一个单元选出来的工程树。

每个单元从冻结起点复制出若干份，每份在自己的容器里跑，互相看不见。跑完以后，判定器逐份检查这一单元的规则清单。只有每条规则都通过，这一份才算通过。通过的份里取第一名，把它的工程树冻结成下一单元的起点。

这样，比较的单位从一次完整运行变成一条链。每一段交接的工程树都通过了这一段的规则，后面的比较才有共同对象。

这里有一个细节：每份候选不是随便加。起点份数来自以往运行里这个单元出过问题的份数加一。没出过问题的单元只跑一份。如果一轮全不通过，就把份数按倍率扩大，再补跑新增的份，已跑完的份不重跑。份数到上限仍然没有一份通过，就写提醒文件，终止这条链，交给人处理。网关故障不算候选失败，等网关恢复后重试同一回合。

这条规则听起来琐碎，它解决的是一个很实际的问题：随机性很大的任务里，不能因为一次坏运气就把一个候选判死，也不能无限加跑把成本拖垮。

## 9:00–13:00 一个单元内部：回合、收尾、失败与上限

（画面：一个单元里的加跑与出口 → 一份内部的回合与收尾）

一个单元里，还要回答两个问题：一份候选跑多久，什么时候算跑完。

每份候选最多三个回合，每个回合有实际时间上限。回合结束后做收尾判定。有的运行外壳能发出完成信号，没有这个信号就当作没有收尾；有的运行外壳以进程结束作为收尾。没有收尾，就在同一个会话上续跑下一回合。

模型网关不可用时，这一回合不计入候选成绩，等网关恢复后重试同一回合。这样做的目的，是不要把网关故障当成候选不合格。

一份候选跑完后，收集产物差异，交给判定器。判定器只读证据，不运行被测技能。它看不到运行时的上下文，也不会被运行时的自述带着走。

## 13:00–17:00 判定器：把“我觉得”变成可核对的结果

（画面：规则清单 → 冻结证据 → 独立验证会话 → judge.json）

每个单元有一份规则清单。比如 spec 单元有五条规则：完成标记是否齐备、页面清单是否和 Android 源对得上、每个页面条目是否带依据、有没有越界、未覆盖的部分有没有如实标注。每条规则都写成一句可以判定的要求，并写清证据形态。

判定时，先把候选的产物、会话和产物差异冻结成一份只读证据。然后每条规则起一个独立的只读验证会话。会话只拿到冻结证据和规则，不加载运行时的技能、规则和扩展。它必须交回一个结论和证据：通过、不通过，或者无法观察。超时、没有交回、证据不足，都记成无法观察，不能算通过。

这里有两个纪律。第一，判定器不运行被测技能，只读证据。第二，判定会话和产出会话隔离，产出会话里的自述不算证据。这样，判定结果可以被复核，也不会被运行时的上下文带偏。

判定结果有三种读法。二值结果是每条规则的通过、不通过、无法观察。不加权分数是通过条数除以规则总数。加权分数先看必过规则：一条必过失败，整份淘汰；必过全过，再按普通规则的通过条数排序。这样同一份结果既能回答能不能用，也能回答哪一份更好。

## 17:00–21:00 DoG：把模糊目标拆成可检查的图

（画面：根节点 → 组合节点 → 叶子 → 失败传播 → 整体断言）

上一节一直在说规则清单，但规则清单从哪里来？很多目标不是一条命令能判的，比如这次迁移做得好不好。DoG 的做法是把这句话拆成一张有向无环图：根是一个整体目标，子节点是它可以失败的方式，叶子是一条条可以独立判定的检查。

叶子有两种判据。程序化判据交给脚本，输入是冻结副本，输出通过、失败或无法观察。Agentic 判据交给独立的只读会话，用一句自然语言说明要判什么、什么算不合格。组合节点只负责组合子节点的结果，失败按规则向上传播。组合节点还可以有一个整体断言：每个子项都过了，作为整体是否成立；整体断言只能降级，不能把失败改成通过。

DoG 的价值在于把“我觉得”拆成可以分别检查的失败方式。把图做大不增加价值，还会提高判定成本，所以图本身也需要约束。

## 21:00–24:00 冻结与继承：改了什么就只重判什么

（画面：对象 → 内容哈希 → 判据身份 → 继承）

每次判定都要先冻结对象。文件按字节算哈希，目录按文件清单算哈希，git 目标解析到具体提交。验证时用的是冻结的字节，不是后来的活文件。

判定也有身份。程序化判据的身份是脚本内容；agentic 判据的身份是判据文字和背景。对象摘要和判据身份合在一起，得到一个继承标识。重跑时，如果这个标识与上一次终态运行一致，就直接继承上次结论，不再起验证会话。对象、判据、背景任何一个变了，就重新判定。

这就是改图要重判多少的回答：只重判变了的目标；没变的继承上次结论，所以迭代只为真正改动的部分付钱。

这里有一个边界要如实讲：继承不重新验证。模型行为漂移在标识不变时看不见。agentic 判定是单次的，没有投票。这些限制不能藏起来。

## 24:00–27:00 DDoG：让图从真实失败里长出来

（画面：静态图膨胀 → 根节点 → 候选 → 正式 → 退休）

DoG 解决的是怎么拆，但它没有解决拆完以后图会不会膨胀。静态图写久了，很多节点几乎不会失败，却一直要付判定成本。DDoG 换了一个做法：根节点来自用户目标，候选节点来自真实失败。

父节点判定交付物时，如果发现一种现有子节点没有覆盖的失败方式，就提交一个新的候选子节点，并附上交付物原文作为证据。候选不单独起判定会话，由父节点在下一次判定里一起看。候选失败次数超过两次、失败率超过百分之二十，才转为正式节点。正式节点成功率达到百分之九十，开始退休评估；至少五个过往失败案例，父节点和子节点判定的一致率超过百分之八十，才退休。退休后只在父节点里判定，不再单独开会话。

这样，图只保留真实有用的检查项。没有真实失败支撑的节点不会长出来，长期不出问题的节点会退出。图不会无限膨胀，判定成本也不会一直涨。

## 27:00–31:00 自迭代：定位、归因、改写、复跑

（画面：失败 → 定位 → 归因 → 改写 → 质量门 → 复跑）

现在有了稳定的定位和判定，才可以谈自迭代。

一次失败先定位到单元、规则和证据。比如 spec 单元的 S1 失败，证据是 feature-index 缺失。定位要能指到具体文件和具体规则，不能停在“模型不行”这句话上。

然后归因。失败可能来自技能文本、运行外壳或模型。只改能改的那一层。归因到技能文本，才进入改写；归因到运行外壳，去修运行外壳；归因到模型，换模型或调整模型设置。技能文本的改写必须先过 DDoG 的质量门，必过规则全部通过，才允许复跑。

复跑只跑受影响的单元，不重跑整条链。每次复跑至少八轮，用同一套规则比较通过率。提升不够，就回到失败案例，不把一次偶然的好结果写成结论。

上下文不腐化要落到具体做法上。判定会话和运行会话隔离，证据冻结，技能文本只保留单一事实来源；候选、正式、退休的状态只向前变化，历史判定只追加，不覆盖。这样，迭代不会把上一轮的上下文垃圾带进下一轮。

## 31:00–33:00 全景：七条链怎么在 kp3 上一起跑

（画面：宿主 → 七条链 → 容器 → 共享判定器 → 看门狗 → 设备隧道）

这套机制不是只在一台机器上跑一条链。宿主是 kp3，七条链各自一个运行外壳，每条链有自己的家目录和容器镜像。候选容器挂载工程副本、会话、只读的 Android 源工程和鸿蒙命令行工具链。所有链共用一个判定器服务。

每条链有看门狗和提醒目录。单元到上限仍没有通过，写 no-winner 提醒；判定器不可用，写 judge-unavailable 提醒。设备单元需要模拟器，鸿蒙和安卓模拟器跑在 Mac 上，通过隧道给 kp3 上的容器使用；其它单元不接设备。

## 33:00–34:00 边界：它保证什么，不保证什么

（画面：保证与不保证）

这套机制保证的是定位、比较和复跑的口径：失败能指到单元、规则和证据；判定会话与产出会话隔离；对象和判据有身份；改了什么就只重判什么。

它不保证最守规矩的一份一定最好。技能文本本身可能有错，遵循得好不等于交付质量高。它也不替人做最终验收。判定器有随机性，继承不重新验证，证据有上限，设备检查在 kp3 上只能记无法观察。这些边界要如实写出来，失败本身也是产出。

## 34:00–35:00 时间线与结果

（画面：时间线 → 七个外壳完成度）

这条机制不是一次设计出来的。最早只有 DoG 原型，把非形式化目标拆成图。后来把迁移流程切成 57 个单元，七个运行外壳一起跑，证明规模上可行。再后来发现静态图会膨胀，转到 DDoG。现在做技能自迭代实验。

结果页只回答一个问题：同一套规则下，七个运行外壳各完成多少个单元。dsh、miniswe、omp 完成 57 个；codex、pi 完成 55 个；claude 完成 3 个；deveco 完成 2 个。这是完成度，不是质量排名。差异来自运行外壳和模型，具体原因要按运行记录分别归因。

另一条本地单链的账是 84 份候选、81 份跑完、328 条通过、4 条不通过、11 条无法观察，成本 59.9 美元。它和七链不是同一组实验，我不把两组数字相加。另一组判定器重复标定是 12/15 一致，两次必过规则集合相同。

技能自迭代现在跑 3 个单元，每个 8 轮，还没有结果。今天不写提升百分比，等结果出来再用同一套规则比较。

回到开头那句话：先定位指令违反，再固定比较对象，再让判定可复核，只改归因到技能的部分，只重跑变化的部分。这样，遵循度提升才是可复核的。
